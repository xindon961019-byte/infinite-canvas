# Infinite Canvas 独立后端接入设计文档

## 1. 文档状态与交付边界

本文件是独立后端与前端接入的实施契约，用于替换此前的概念方案。只设计，不代表功能已实现或已验证。代码审查、故障注入、真实渠道验收与部署验证仍是交付条件，任何文档都不能保证实现绝无缺陷。

已确定的架构：后端独立仓库 `infinite-canvas-cloud`；当前 fork 保留浏览器本地优先；后端提供私有媒体托管、模型读取链接、不可变备份快照和恢复支持。

第一版明确采用：
- 单工作空间、管理员在服务端配置访问令牌，不提供公开注册。
- Node.js、TypeScript、PostgreSQL 元数据、服务器磁盘媒体存储。
- 手动创建快照、按选择的业务域恢复；不实现自动双向合并。
- 模型调用继续由前端向现有渠道发起。
- 主体库是后续业务功能，不是后端接入的前置条件。
- 前后端独立发布，公网通过现有 Nginx 的同域路径连接。
- 不复制整个 WebDAV 同步算法，不实现没有实际使用者的通用传输框架。

本次授权是文档编写。容量、期限、并发、超时等行为边界尚未得到用户确认，本文件给出配置名称、适用环节与失败语义，不虚构已批准默认值。开发可按契约实现；生产启用前必须完成第 19 节配置确认。

## 2. 当前代码事实与范围

### 2.1 本地数据来源

| 业务域 | 当前来源 | 云端 v1 范围 |
| --- | --- | --- |
| canvas | use-canvas-store 中 projects、deletedProjects | 项目、节点、连线、浏览器内的 chatSessions、视口与项目属性 |
| assets | use-asset-store 中 assets | 当前文字、图片、视频素材及其元数据 |
| image-workbench | image_generation_logs localforage 实例 | 图片工作台持久化生成记录 |
| video-workbench | video_generation_logs localforage 实例 | 视频工作台持久化生成记录 |
| 图片文件 | image_files 实例 | 上述业务记录引用到的文件 |
| 音视频文件 | media_files 实例 | 上述业务记录引用到的文件 |

所有实例数据库名为 `infinite-canvas`。业务状态由 `app_state` 中 `infinite-canvas:canvas_store` 和 `infinite-canvas:asset_store` 保存，值包含 Zustand 的持久化封装，不能直接替换为裸数组。

实际 WebDAV 业务域是 `canvas/assets/image-workbench/video-workbench`，不是 `image-logs/video-logs`。当前素材类型不包含独立音频素材；画布中的音频文件仍纳入媒体备份。

### 2.2 已有实现的限制

- `app-sync.ts` 会读取远端、合并并写回本地，再上传；不能直接用作单向备份。
- 现有增量上传主要通过文件存在和字节数判断，不提供 SHA-256 内容一致性。
- 部分媒体只保留外部 URL，未必有本地 Blob。
- 恢复生成记录的现有方法会先 clear 再逐条写入，不提供跨域原子恢复。
- 画布持久化存在 400ms 的延迟保存，setState 完成不等于落盘完成。
- `localforage-storage.ts` 当前存在 localStorage 回退；云端恢复必须识别它，不能把配额错误当成成功写入另一个位置。
- 图片、视频工作台、媒体服务、清理操作各有写入入口，单纯阻止按钮不能阻止后台任务写数据。
- 视频脚本接收图片 Data URL、视频 File[]、音频 File[]，没有云端媒体工具。

### 2.3 明确排除

第一版不备份全局配置 store、API Key、WebDAV 密码、Cloud 令牌、模型调用脚本、浏览器 UI 偏好、未持久化草稿、浏览器缓存、任意插件私有数据库和本机 Agent 文件历史。

canvas 中已有的浏览器 chatSessions 与本机 Canvas Agent 历史是不同数据，不能宣称后者已备份。音频工作台、主体库只在确实实现独立持久化域后增加。

界面使用“备份画布、素材、生成记录及关联媒体”，不使用“备份所有数据”。

## 3. 系统边界与数据流

```text
浏览器：原有编辑、localforage、用户渠道密钥
  ├─ API 请求 ───────────────→ 用户配置的模型渠道
  └─ Cloud Client ───────────→ Nginx /api/cloud/v1
                                  ↓
                              独立 Cloud 服务
                               ├─ PostgreSQL
                               └─ 私有文件目录
模型渠道 ── GET/HEAD ────────→ Nginx /media-access/<token>
                                  ↓
                              Cloud 验签与流式读取
```

后端不接收用户渠道 Key，不代理模型计费请求，不根据任意外部 URL 抓取资源。媒体上传来源是用户已选择的文件或浏览器已获取的 Blob。

未启用 Cloud 不主动上传。Cloud 离线不影响普通本地编辑；需要新建媒体链接的模型任务会明确失败，不能假装仍能生成。

## 5. 协议与身份

基础路径 `/api/cloud/v1`。除模型读取端点外，所有接口包括状态、列表、缺失文件检查和下载均要求 Bearer 鉴权。响应默认 `Cache-Control: no-store`。

服务身份：
- `serverId`：首次初始化持久化生成，升级不变，重建数据服务时重新生成。
- `workspaceId`：令牌映射出的工作空间 ID，客户端不可指定访问别人的空间。
- 单用户 v1 也在所有查询和唯一约束中带 workspaceId，为隔离提供实际边界。
- Token 在服务端验证时使用安全比较；仅保留需要的校验材料，服务端文件权限限制访问。
- 签名密钥与主访问令牌独立，支持 key ID；凭据轮换不等于服务器身份变化。

所有 JSON 请求拒绝未知顶层字段、重复对象键、非法 Unicode/非有限数值、危险原型键。大小受配置限制。业务扩展字段按第 8 节规则处理。

错误统一：
```json
{"error":{"code":"MEDIA_MISSING","message":"备份缺少媒体文件","requestId":"req_example","details":{"mediaIds":["media_example"]}}}
```

| HTTP | code | 客户端处理 |
| --- | --- | --- |
| 400 | INVALID_REQUEST / HASH_MISMATCH | 修正请求，不自动重试 |
| 401 | UNAUTHORIZED | 停止并重新配置凭据 |
| 404 | RESOURCE_NOT_FOUND | 无权限与不存在使用相同结果 |
| 409 | IDEMPOTENCY_CONFLICT / INVALID_STATE / RESOURCE_IN_USE | 查询状态或明确处理冲突 |
| 413 | PAYLOAD_TOO_LARGE | 告知实际限制 |
| 415 | MEDIA_TYPE_NOT_ALLOWED | 改用支持格式 |
| 422 | INVALID_MANIFEST / UNSUPPORTED_DOMAIN_VERSION | 拒绝提交或恢复 |
| 429 | RATE_LIMITED | 按批准的重试策略与 Retry-After 处理 |
| 507 | STORAGE_FULL / WORKSPACE_QUOTA_EXCEEDED | 停止上传，保留本地数据 |
| 503 | NOT_READY / POLICY_NOT_CONFIGURED | 禁止业务写入 |

日志只记录 requestId、对象 ID、结果、耗时和字节数。不得记录原始清单、提示词、Authorization、签名 URL 或上传内容。

## 6. API 完整契约

所有 ID 为服务端生成的不可猜测字符串。客户端 backup 创建幂等键用随机 UUID，通过 `Idempotency-Key` 请求头发送。摘要为小写十六进制 SHA-256，长度严格校验。

所有 JSON 时间为 UTC ISO 8601；数量和 bytes 为非负安全整数，文件 bytes 必须大于零。ID 仅接受服务端声明的字符集合，不包含路径分隔符。JSON 请求 Content-Type 不符返回 415。非法或过期 cursor 返回 400，不回到第一页；cursor 绑定空间与排序条件，采用签名不透明游标。服务端统一生成 requestId，内部错误不返回堆栈。

### 6.1 GET /status

返回：
```json
{
  "service":"infinite-canvas-cloud",
  "serverId":"srv_example",
  "workspaceId":"ws_example",
  "apiVersion":1,
  "manifestVersions":[1],
  "domainVersions":{"canvas":[1],"assets":[1],"image-workbench":[1],"video-workbench":[1]},
  "capabilities":{"media":true,"backups":true,"restore":true,"automaticMerge":false},
  "policy":{"configured":false}
}
```

生产开启时 policy.configured 必须为 true，并返回第 19 节的有效客户端边界。storageVersion 只用于服务端迁移诊断，不作为前端兼容判断。恢复由 manifestVersion 和域版本共同决定。

### 6.2 POST /media/resolve

用途：按内容摘要查找当前空间已有媒体，禁止全局跨用户存在性探测。

请求：
```json
{"files":[{"sha256":"<64 hex>","bytes":123456}]}
```

响应：
```json
{"found":[{"sha256":"<64 hex>","mediaId":"media_example","bytes":123456,"mimeType":"audio/mpeg"}],"missing":[]}
```

missing 为未找到的摘要数组。请求内相同摘要、不同大小返回 400。批次上限按配置，客户端拆批。

### 6.3 POST /media

multipart 字段：file（二进制，恰好一个）、sha256、purpose。purpose 取 backup/reference-image/reference-video/reference-audio；原文件名可用于显示，不参与磁盘路径。

成功首次 201，当前空间已有相同内容时 200；均返回：
```json
{"mediaId":"media_example","sha256":"<64 hex>","bytes":123456,"mimeType":"audio/mpeg"}
```

后端流式写临时文件，同时计算哈希和字节数；完成后检测 MIME，验证摘要、尺寸、类型，才发布 ready 记录。参考用途只接受配置中的对应图片/音视频类型，备份仅接受被支持域引用的媒体类型，不开放任意文件托管。

取消和断网不创建 ready 记录。重试整个文件，v1 无分片续传；禁止对外声称支持断点上传。支持重试去重，不意味着恢复部分上传字节。

### 6.4 GET/HEAD /media/:mediaId/content

私有读取，按当前空间验证。返回服务端检测 MIME、Content-Length、nosniff；GET 返回字节，HEAD 无正文。不可用文件返回 404 或 503，不能返回空文件。

### 6.5 POST /media/:mediaId/access-grants

请求：
```json
{"purpose":"model-reference"}
```

响应 201：
```json
{"grantId":"grant_example","mediaId":"media_example","url":"https://infinite.zemra.cn/media-access/<token>","expiresAt":"<UTC ISO8601>"}
```

期限服务端决定并来自已确认 policy，客户端不能任意延长。不要接受任意 provider 字符串来绕过期限或权限。

### 6.6 GET/HEAD /media-access/:token

无需用户 Cookie 或 Bearer，但必须验证签名、grant 状态、workspace、mediaId、expiry 和 key ID。token 是 Bearer 能力凭据，获得者可以在有效期间读取，不能宣称仅某一家模型可用。

允许重复 GET/HEAD 和合法 Range，使用成熟 HTTP 文件服务库；单范围返回 206、无效范围 416，多范围按所选库明确支持或拒绝，禁止手写解析。响应禁止共享缓存；URL 不重定向登录页或 HTML。

不以读取一次为“模型已完成”，不在创建视频任务后立即撤销。链接签发时不存在的媒体返回错误；媒体删除、授权撤销、过期后拒绝读取。

DELETE /media/:mediaId/access-grants/:grantId：鉴权、归属检查，撤销后重复操作仍 204。

### 6.7 DELETE /media/:mediaId

仅当前工作空间所有者可用。被 draft/committed 备份或未过期 grant 引用返回 409 RESOURCE_IN_USE。无引用时从逻辑索引删除，重复删除 204。物理文件垃圾回收见第 11 节。上传和模型使用不触发自动删除。

### 6.8 POST /backups

请求头 Idempotency-Key 必填。请求体：
```json
{"manifest": {"app":"infinite-canvas","manifestVersion":1,"clientId":"client_example","capturedAt":"<UTC ISO8601>","domains":[],"files":[]}}
```

完整清单格式见第 8 节；上例数组仅示意，不是有效完整备份。

响应：
```json
{"backupId":"backup_example","state":"draft","manifestSha256":"<64 hex>","missing":["<64 hex>"],"mediaBindings":[]}
```

服务端先校验并规范化清单，使用 RFC 8785 兼容库计算摘要。幂等键在当前空间唯一；同键同摘要返回原对象，同键不同摘要返回 409。清单创建后不可修改，修改内容需新建备份。

mediaBindings 返回清单中已经存在的 `sha256/mediaId/bytes/mimeType` 映射。不完整上传由 missing 驱动，无需单独 putManifest 接口。

创建首次返回 201，幂等重放返回 200。清单至少选择一个域，每个域最多一次；域内空列表是有效的空域，恢复时会清空该域，必须在确认框明确显示。files 只包含被 mediaRefs 使用的文件，所有 fileKey 引用必须可解析，未引用文件、重复 pointer、同一 pointer 指向不同内容一律 422。

### 6.9 GET /backups/:backupId

返回 state、manifest、manifestSha256、mediaBindings、missing、createdAt、committedAt（未提交为 null）。draft 仅供创建者所在空间恢复上传；只有 committed 可恢复。

commit 响应丢失时，客户端必须先查询该接口，不创建重复快照。未知其他空间 ID 一律 404。

### 6.10 POST /backups/:backupId/commit

无请求体。验证所有清单摘要对应的 ready 文件，写入完整媒体关联并在 PostgreSQL 事务中转 committed。缺文件返回 409 MEDIA_MISSING，状态仍 draft。

成功返回：
```json
{"backupId":"backup_example","state":"committed","manifestSha256":"<64 hex>","committedAt":"<UTC ISO8601>"}
```

同一对象重复 commit 返回相同 committed 结果。并发 commit 串行化事务，不能生成两份快照。客户端时钟不决定排序或冲突。

### 6.11 GET /backups?cursor=...

只列 committed，按服务端 createdAt、backupId 稳定排序。分页大小来自 policy；不无界返回清单。响应 items 为摘要信息、域名称、记录数量、唯一文件字节数，另含 nextCursor/null，不返回整个业务数据。

### 6.12 DELETE /backups/:backupId

draft 变 cancelled；committed 变 deleted。重复同空间删除 204；commit 与删除并发时只允许一个合法事务胜出。删除快照不改变浏览器，不立即删共享媒体。恢复客户端遇到 deleted 停止下载，保留原本地数据。

上述接口就是 v1 全部业务端点。没有独立 mutable domain manifest、覆盖“最新快照”或自动 merge 接口。

## 7. PostgreSQL 与文件一致性

最少表：

| 表 | 关键字段与约束 |
| --- | --- |
| service_meta | serverId、storageVersion |
| workspaces | id、quotaUsed、配置状态 |
| media | id、workspaceId、sha256、bytes、mimeType、state、createdAt；UNIQUE(workspaceId,sha256) |
| upload_reservations | id、workspaceId、reservedBytes、tempPath、状态 |
| backups | id、workspaceId、idempotencyKey、manifestSha256、manifestJson、state、createdAt、committedAt；UNIQUE(workspaceId,idempotencyKey) |
| backup_files | backupId、sha256、mediaId nullable；唯一 backupId+sha256 |
| access_grants | id、workspaceId、mediaId、keyId、expiresAt、revokedAt |
| maintenance_jobs | id、操作类别、对象、状态与错误 |

通过迁移显式建立外键。状态变更与配额更新使用事务。draft 清单同样保护媒体免遭删除；blob 就绪后 commit 绑定 mediaId。跨空间不做物理去重。

### 7.1 PostgreSQL 类型、约束与事务

- ID 使用 `text`，保留 API 的 ID 格式；时间使用 `timestamptz`，由服务器生成。字节数与配额使用 `bigint` 并设置非负 CHECK；`pg` 默认返回的 bigint 字符串不得直接隐式转换。API 若输出 JSON number，必须先验证不超过 JavaScript 安全整数范围，超出则拒绝该输入，不能截断。
- `manifestJson` 使用 `jsonb`；摘要仍按第 8 节规范化原始 JSON 值计算，不能依赖 PostgreSQL 的 JSON 文本输出或键顺序。状态字段设置明确 CHECK，必填字段 NOT NULL。
- 子表携带 workspaceId，以复合唯一键和复合外键约束资源归属；backup_files 的备份外键及媒体外键均包含 workspaceId。mediaId 未绑定时允许 NULL，commit 前必须全部绑定。删除使用 RESTRICT 和业务状态流转，不能级联误删仍被引用的媒体。
- 为 `(workspaceId, createdAt, id)` 列表查询、各外键引用列、媒体引用检查及授权有效期查询建立索引；唯一约束由数据库裁决，并发去重不能仅靠先 SELECT 再 INSERT。
- 通过 `pg.Pool` 管理连接。一次事务必须 `pool.connect()` 获取同一个 client，依次 BEGIN、全部 SQL、COMMIT；失败 ROLLBACK，finally 释放连接。不可用多次 `pool.query()` 拼接事务。所有外部值参数化。[node-postgres 事务文档](https://node-postgres.com/features/transactions)
- 默认使用 READ COMMITTED，并为配额、媒体状态和快照状态的读改写显式加锁。v1 每次资源变更先锁 workspace 行，再按 ID 排序锁备份和媒体行；上传预留/结算、commit、删除、授权签发和 GC 都遵循同一顺序。事务内重新校验引用与状态，使用条件 UPDATE 防止非法状态迁移。该约定以空间内短事务串行化换取可审查的一致性；不能有某个清理脚本绕过它。[PostgreSQL 锁机制](https://www.postgresql.org/docs/current/explicit-locking.html)
- 不在数据库事务内等待浏览器上传、模型调用或大文件复制。上传预留与最终结算分为短事务；文件清理先在事务内锁定并标记 deleting、确认无引用，再删除文件，最后事务结算。deleting 状态禁止新增引用或上传复用；失败保留状态供巡检，不能提前扣除配额。
- 同摘要上传竞争时使用唯一约束及冲突处理：只由首次转为 ready 的事务计入实际用量，其余请求释放各自预留；预留释放和结算具备幂等状态条件。已有 ready 记录的大小/类型不一致视为损坏并拒绝复用。
- 连接中断、锁等待超时或死锁不得报告成功。SQLSTATE `40001`/`40P01` 仅在明确配置重试策略后重做整个幂等事务；不能单独重放其中一条 SQL，更不能重试付费模型任务。COMMIT 响应丢失时按媒体摘要或快照幂等键查询最终状态。
- 数据库不可用时依赖它的 API 返回 503，写入关闭，不回退到本地文件数据库。连接池大小、获取连接等待、statement_timeout、lock_timeout 及事务重试策略均在第 19 节确认，连接池容量需给迁移和运维预留连接。

### 7.2 文件发布与故障恢复

物理路径 `data/files/<workspaceId>/<sha256前两位>/<sha256>`；临时路径由服务端随机生成，位于同一文件系统。用户输入不得控制目录，读取时禁止符号链接逃逸。

上传发布顺序：
1. 在事务内检查空间与保留容量；并发上传不能各自通过同一份剩余配额。
2. 流式写临时文件，执行实际字节上限。
3. 验证哈希、MIME、字节数，flush/fsync 文件。
4. 安全原子发布到最终路径，若已有文件则验证一致后复用，绝不覆盖不同内容。
5. 在事务内插入 ready 媒体并结算真实配额；相同摘要竞争只保留一条记录。
6. 返回响应。

若第 4 步后崩溃，允许留下未索引文件，但不能出现索引显示成功、文件不存在。启动巡检把孤立文件列为待检查；不根据文件数或大小自动删除。数据库清单存 manifestJson，避免数据库提交与外部 JSON 文件提交的双重原子性问题。

磁盘满、哈希不一致、权限不足都不得返回成功。部署时模拟上述中断位置验证。

## 8. 备份清单与域编解码

### 8.1 三类版本

- apiVersion：HTTP 协议版本。
- manifestVersion/domainVersion：备份载荷格式和业务域格式。
- storageVersion：后端自身数据库版本。

后端不依据前端 commit 猜测兼容性。上游数据变化不允许写成同版本不同含义。未知版本可保留下载原始文件供人工处理，但不得自动恢复或覆盖。

### 8.2 Manifest v1

```ts
type ManifestV1 = {
  app: "infinite-canvas";
  manifestVersion: 1;
  clientId: string;
  capturedAt: string;
  sourceCommit?: string;
  domains: Array<{
    name: "canvas" | "assets" | "image-workbench" | "video-workbench";
    domainVersion: 1;
    data: unknown;
    mediaRefs: Array<{
      pointer: string;
      fileKey: string;
      representation: "blob-url" | "data-url" | "storage-key";
    }>;
  }>;
  files: Array<{
    fileKey: string;
    sha256: string;
    bytes: number;
    mimeType: string;
    originalStorageKey?: string;
  }>;
};
```

pointer 是指向该域 data 中明确字段的 RFC 6901 JSON Pointer，使用成熟库。fileKey 在清单内唯一；同一内容允许不同本地引用，但只上传一份摘要。mediaRefs 的所有 pointer 必须存在，目标值在传输清单中置 null，恢复时按 representation 重新填充。业务 Schema 在这些列明位置允许 null，其余字段严格校验。

不得把 blob URL 当文件；不得把 mediaId 当跨服务器稳定标识。后端通过 files 摘要生成 mediaBindings，恢复下载统一使用绑定的 mediaId。

### 8.3 四域具体编码职责

| 域 | data 根结构 | 处理 |
| --- | --- | --- |
| canvas | {projects, deleted} | 来自 projects/deletedProjects；保留项目 ID、节点 ID、连线、组关系、浏览器聊天和视口 |
| assets | {assets} | 保留文字/图片/视频素材结构 |
| image-workbench | {logs} | 使用当前工作台持久化记录，不序列化 React 或函数 |
| video-workbench | {logs} | 保留可解释的历史结果，不自动恢复运行中的远端任务轮询 |

实现域编解码器时必须逐字段列出实际持久化类型，保存为 JSON Schema 和测试夹具。unknown 只是文档 TypeScript 表达载荷多态，不能在服务端直接跳过校验。

媒体位置包括节点 content/storageKey、images 备选图、引用列表、资产 coverUrl/dataUrl/url、记录输入参考和结果、浏览器聊天附件。不同 URL 指向不同封面时分别保存，不能用视频 URL 替换图片封面。

优先以有效 storageKey 读取 Blob，再处理 data URL 和可读取的 blob URL。未本地化的 HTTP(S) 媒体由浏览器通过现有网络路径获取并转换 Blob；不把用户渠道凭据转发给 Cloud。

### 8.4 不完整与扩展数据策略

v1 不提交“媒体丢失但成功”的快照：
- 引用文件缺失、blob URL 失效、外部媒体无法下载：报告域、记录、字段与原因；备份不能提交。
- 用户可修复媒体，或明确取消该业务域重新创建备份；不能自动跳过文件。
- 普通文本里的网址不是媒体，不自动抓取。
- 自定义节点及扩展元数据需要登记对应版本的 codec；未知扩展阻止该域备份并展示原因。
- 不扫描/改写任意字符串中的业务 ID，也不通过正则替换全部 URL。
- 程序管理的敏感配置字段使用字段白名单排除。用户在提示词/聊天中手工写入的秘密无法被可靠自动识别，应提示正文将原样备份，不能宣称绝无敏感内容。

### 8.5 数据一致性捕获

等待各 store hydration；协调器暂停编辑与后台业务写入，flush 所有已排队写入后取得四域深拷贝和所需 Blob 引用，再释放编辑。快照 capturedAt 表示捕获时间，不表示上传完成时间。

不能在用户继续编辑时逐域读取，形成不同时间的项目与素材。捕获阶段失败不创建远端会话。网络上传期间可以继续编辑，捕获对象不跟随 store 变化。

取得 Blob 引用不代表始终持有全部文件的 ArrayBuffer；大文件读取与哈希必须分块。远程媒体捕获固定为本轮读取到的字节，不能在重试时重新下载变化后的 URL 并继续使用原清单摘要；需要改变字节时新建快照。

大量媒体按批准的并发逐个哈希和上传，不 Promise.all 把所有 ArrayBuffer 留在内存。用成熟增量哈希库在 Worker 内处理文件；服务端再次验证，不能信任客户端摘要。

## 9. 恢复协议：可回滚写入而非假定原子

### 9.1 v1 产品行为

只提供“恢复所选业务域”，所选域整体替换，未选域保留。确认框显示本地和快照记录数、将被替换的域、恢复副本位置。

v1 暂不提供“导入为新项目”，避免尚未定义的节点引用、插件 ID 和跨域引用重映射。现有项目导入功能继续独立使用。

恢复不删除原始媒体；对每个待恢复文件分配新的本地 storageKey，再由 mediaRefs 改写所选域引用，防止同名 storageKey 覆盖未选域数据。项目/节点等业务 ID 在整体恢复中保持不变。

### 9.2 写入协调与跨标签页

在原应用挂载、Zustand hydration 和后台服务启动前运行恢复启动检查。发现未完成恢复时先进入专用恢复页面，不加载业务页面。

使用同源 Web Locks 协调：
- 正常业务写入在 shared 锁内执行并返回真实完成 Promise。
- 捕获和恢复使用同名 exclusive 锁。
- 所有 store 持久化、图片/媒体写入删除、日志写入、WebDAV 本地应用、导入、清空数据、自动清理都必须经过协调器。
- 恢复前暂停生产新写入的任务，等待已发起写入排空；画布显式 flush/cancel 已有计时器。
- exclusive 恢复期间到达的写操作不能在恢复后原样排队执行；携带旧 generation 的写操作必须被拒绝并提示刷新。
- 广播恢复状态与新 generation，用于其他标签页停止编辑和重载；广播只改善体验，不能代替锁。
- generation 持久化，每次实际写入在锁内验证，不只检查内存。
- 旧版本标签页不支持协议时必须关闭；界面要求用户关闭旧标签页，无法证明不存在旧写入端时禁止声称跨版本并发安全。
- 不支持 Web Locks、IndexedDB 或持久化失败时禁用覆盖恢复，不退化成无锁写入。

锁获取顺序必须固定为“宣布准备 → 停止产生新操作 → flush 已有操作 → 等待 shared 写完成 → 获取 exclusive → 应用/回滚”。禁止持有 exclusive 后调用会重新申请 shared 锁的 flush/setItem，否则会死锁。持有 exclusive 的恢复代码使用仅模块内部可访问的原始存储入口，不经普通写入包装器。

普通写入必须从产生状态变更/安排延迟任务时就登记 operation，而非等计时器执行才登记。准备恢复的标签页通过 BroadcastChannel 请求其他支持协议的标签页暂停并 flush；任一标签页未确认时保持等待并允许用户取消，不以超时视为确认。拿到 exclusive 后再次验证 generation 与未完成操作，失败释放锁并重新预检。

恢复 journal 的 committed 标记与 nextGeneration 必须在同一个 IndexedDB 事务内提交；正常写入在 shared 锁内同时检查 generation 与 journal 是否存在未完成恢复。若遇到 applying/rolling_back，拒绝业务写入并进入恢复页。不能依赖 BroadcastChannel 消息先到达，也不能让页面内旧 Zustand 状态在锁释放后覆盖新状态。

Cloud 恢复路径不使用 localStorage 回退。若当前旧数据实际来自回退存储，预检返回 LEGACY_STORAGE_LOCATION，提示先通过原导出方式保全并解决存储环境，不静默迁移。

### 9.3 Journal 结构与状态

独立 IndexedDB/localforage 存储 `cloud_restore` 保存：
```text
restoreId、backupId、serverId、workspaceId
manifestSha256、selectedDomains
phase: staging/prepared/applying/committed/rolling_back/rolled_back
previousGeneration、nextGeneration
原始业务持久化键值与存在性
待写目标键值与摘要
已创建的媒体 storageKey 列表
错误与最后成功阶段
```

journal 和原始值只保存在浏览器，不上传服务器。原始值必须在任何覆盖前写入并回读校验；失败则不能进入 applying。

### 9.4 恢复执行

1. 查询 committed 快照，校验域版本、摘要、所有引用和服务身份。
2. 下载所需媒体到 staging，逐个验证哈希；期间不覆盖业务数据。
3. 用户确认恢复范围，按第 9.2 节顺序暂停生产者、flush、排空，再获取 exclusive 锁。
4. 读取真实落盘旧值，记录存在/不存在、日志键集合，保存 prepared journal。
5. 为恢复媒体创建全新 storageKey，生成新 Blob URL/Data URL 或 storageKey 引用。原有媒体不修改。
6. 持久化 applying 状态后，逐域写入目标封装值；日志先写目标记录，再删除目标集合之外的旧记录。原日志已在 journal 中保存。
7. 回读所有目标记录并验证目标摘要、媒体引用可读取。
8. 持久化 committed journal 和 generation，保持业务挂载阻断，刷新页面。
9. 启动检查重新校验 committed 数据，通过后允许 hydration；资产、节点和日志由 storageKey/媒体表重建本次会话 URL，绝不使用上次会话 blob URL。
10. journal 转为可选本地恢复副本。v1 不自动裁剪；空间不足提示用户显式处理。

localforage 跨实例没有此方案所需的统一事务，因此这是日志辅助的可回滚应用，不是多个表瞬间原子更新。

原始值备份包含日志的每个键及其值、app_state 原始封装字符串、Zustand version 和不存在键的标记。回滚逐键 set/remove，重建原日志键集合；不能把不存在值写成 null 冒充恢复。数据回读比较使用域规范化后的持久化载荷，排除当前会话 blob URL，避免每次生成 URL 都导致摘要变化。

若目标记录原来没有 storageKey，codec 必须根据实际类型补充支持的持久引用并清空对应会话 URL；类型不能容纳 storageKey 的媒体字段按 data-url 表达恢复，不向其写入一次性 blob URL。不允许在无对应 hydration 实现的字段使用 blob-url representation。每个 codec 必须同时提供 encode、decode、hydrate、listReferences 和 validate，测试覆盖刷新后二次读取。待恢复映射和所创建键在应用前写入 journal，崩溃重试复用同一组映射，不反复生成新文件键。

取消只在 staging/prepared 阶段立即生效；applying 阶段点击取消必须触发完整回滚，不能停止在部分应用状态。committed 后提供的是新的“恢复原副本”操作，不能把取消解释为撤销远端已提交备份。

### 9.5 崩溃与回滚矩阵

| 中断阶段 | 下次启动处理 |
| --- | --- |
| staging | 原数据未覆盖，允许继续下载或取消 |
| prepared | 原数据未覆盖，校验旧值后取消或继续 |
| applying | 禁止业务挂载，默认进入 rolling_back |
| rolling_back | 幂等逐项恢复原值和原有键集合，直到回读通过 |
| committed | 验证目标完整性；通过后重建 URL 并挂载；失败进入恢复处理 |
| journal 损坏 | 禁止自动写入，提供导出诊断/本地恢复副本，不能用空数据初始化 |

回滚不依赖网络。回滚过程中空间不足或写失败，继续阻止业务挂载并保留 journal，不能显示“已恢复”。新 staging 媒体在确定无引用后由用户显式清理；原媒体不因回滚删除。

## 10. 模型脚本接入

### 10.1 采用按需工具

为 runModelPlugin 新增可选变量：
```ts
type CloudTools = {
  mediaUrl(input: Blob | string, options: {
    kind: "image" | "video" | "audio";
  }): Promise<{url: string; expiresAt: string}>;
};
```

保留 images/videos/audios 原有参数及内容；只向函数末尾增加 cloud 参数并同步执行器传值、变量说明、复制给外部 AI 的脚本文档和测试。工具继承当前 AbortSignal，不暴露 Cloud Token。

string 只接受现有脚本获得的 data URL 或同浏览器 blob URL；HTTP 外部文件由现有调用流程读取，工具不充当任意 URL 抓取器。Blob 按 kind 校验。图片 Data URL 可转换为 Blob；视频和音频直接用 File。

示意，具体模型请求路径与字段必须按实际渠道文档验证：
```ts
const reference = await cloud.mediaUrl(audios[0], {kind: "audio"});
const content = [{
  type: "audio_url",
  audio_url: {url: reference.url},
  role: "reference_audio"
}];
```

这个示例只证明工具调用方式，不宣称所有名为 H3/Seedance 的渠道接受同一协议。没有参考音频时脚本不调用工具；真实模板要检查数组是否存在。

### 10.2 映射缓存

独立 localforage 缓存键：
```text
serverId + workspaceId + sha256 → mediaId/bytes/mimeType
```

不往所有节点添加 remoteMediaReference。申请链接返回媒体不存在时清除此条缓存并重新 resolve/upload；若本地文件也不存在则明确报错。换 token 后重新确认 workspaceId，换服务器重新建立映射。

不持久化短期签名 URL 到画布、记录或备份；仅用于本次任务内存。无法控制第三方脚本主动记录 URL，但应用自身日志必须脱敏。

### 10.3 失败与计费边界

- Cloud 未配置：调用 mediaUrl 明确报 CLOUD_NOT_CONFIGURED，未使用工具的旧脚本照常工作。
- 文件上传失败：不提交模型生成任务。
- 上传可按幂等内容摘要重试；模型创建请求不能自动重试，除非渠道明确提供幂等保证。
- 模型请求超时且是否创建成功未知：报告“提交状态未知”，保留相关信息供渠道查询，不能自动再扣费创建。
- AbortSignal 中止上传和链接请求；已经提交给渠道的任务未必能取消，必须准确说明。
- 签名到期后原任务 URL 不会被替换；新签发链接只对新请求有效。
- 参考音频属于生成条件，不保证模型逐字复现台词或精确口型。不能将 URL 可访问等同生成质量验收。

## 11. 媒体生命周期与配额

v1 不后台自动删除快照、未引用媒体或本地恢复副本，不设置未经确认的保留天数。提供可审查的列表、引用关系和显式删除动作。

垃圾回收仅由维护操作触发：
1. 列出不被任何 draft/committed 快照和有效 grant 引用的对象。
2. 标记删除候选，在事务内重新确认引用。
3. 使逻辑资源不可再申请授权，读取中的句柄按服务库规则处理。
4. 删除物理文件，记录完成；失败保留任务可重试。
5. 最后更新实际存储统计。

同一空间去重后的 ready 文件计入一次配额，临时上传保留容量也计入。快照清单、数据库与临时空间另有实际磁盘水位检查，不只计算媒体配额。未知长度上传按配置的单文件最大值预留，完成后释放差额；长度声明不能替代流式实际上限。

## 12. 安全边界与隐私

- 备份列表、清单、resolve、私有下载都鉴权，不只保护写接口。
- 单令牌等于同一管理员空间，不能用它为不可信多人提供数据隔离。
- CORS 不是鉴权，同域也要验证 Bearer。
- 自定义脚本在当前页面执行，原来就属于受信任代码；Cloud 工具不把它变成安全沙箱。
- 签名使用成熟 HMAC/JWT 库或标准加密 API，显式绑定算法、版本、grantId、mediaId、workspaceId、expiresAt、keyId，不允许客户端选择算法。
- 模型链接可被持有者转发；可撤销、到期控制与日志脱敏都必须生效。
- Nginx 对 /media-access 不记录完整 URI，应用不打印 token。
- 只提供二进制媒体响应，拒绝 HTML/SVG 等可执行内容用于公网参考；需要这些备份类型时必须另行设计下载隔离。
- v1 后端不接受远程 URL 抓取，消除该入口的内网探测风险。
- MIME 识别只是第一层验证，不等于媒体一定能解码；渠道类型、时长、编码要求仍由模型适配与实际验收决定。
- 文件和数据库目录不位于前端 release，不开放目录列表。
- 生产主令牌与签名密钥分别管理，权限最小化，服务进程不以 root 运行。

## 13. 部署与恢复运维

公网路径：
```text
/                   现有静态前端
/api/cloud/v1/      后端 HTTP API
/media-access/      后端签名读取
```

Nginx 必须保留 API 前缀转发，不能落入 SPA fallback；未知 API 返回 JSON 404。后端本机监听端口由部署配置确定。v1 使用单个后端实例与 PostgreSQL 连接池；数据库支持并发事务。由于媒体仍保存在本机磁盘，暂不部署多实例，不能仅增加进程就假设文件发布和清理已经支持分布式并发。

目录：
```text
/srv/infinite-canvas-cloud/
  releases/<releaseId>/
  current -> releases/<releaseId>
  data/files/
  data/tmp/
  config/
  backups/
```

首次部署：
1. 记录已有服务、Nginx 路由、存储空间和恢复点。
2. 独立上传后端 release，配置服务账号和目录权限。
3. 填写已确认策略及凭据，初始化数据库/serverId。
4. 内网鉴权验证通过后配置 Nginx，校验再平滑 reload。
5. 公网验证上传、下载、HEAD/Range、签名到期/撤销、快照提交与实际恢复。
6. 后端稳定后发布可选前端入口；不开启时不得产生上传。
7. 保留旧应用 release、部署记录及可验证数据备份。

PostgreSQL 使用独立服务或持久化容器卷管理 PGDATA，不放入应用 release，不随代码发布重建。数据库只允许后端和运维网络连接；`DATABASE_URL` 仅保存在后端受限配置中，不进入前端、日志或 Git。应用角色仅授予业务表必要权限；迁移使用独立 DDL 角色，应用不使用超级用户。远程连接校验 TLS 证书。

数据库与媒体必须作为同一个恢复集合备份：
1. 进入维护模式，拒绝新写入，等待已有上传、事务和清理完成；维护状态必须被 API、后台任务及运维清理入口共同遵守。备份失败也不得留下未察觉的永久维护状态。
2. 使用 `pg_dump --format=custom` 导出指定业务数据库，记录 serverId、storageVersion、应用版本、备份标识和全部引用文件的摘要清单。
3. 在维护期间复制清单引用的媒体及必须保留的服务配置，验证数据库归档可读、文件存在且哈希一致，再退出维护。凭据与签名密钥单独加密备份并限制访问。
4. 将完整集合保存到其他故障域。`pg_dump` 自身提供数据库一致快照，但不包含外部媒体，也不包含集群角色；数据库角色及授权用部署配置重建。仅有数据库归档不能视为整站可恢复。[PostgreSQL pg_dump 文档](https://www.postgresql.org/docs/current/app-pgdump.html)
5. 恢复演练使用新建空数据库和独立文件目录，以 `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges` 恢复归档，通过受控迁移角色恢复并重新应用授权；验证版本、配额、外键、快照引用和媒体摘要。不得直接在正在服务的数据库上试恢复。
6. 实际灾难恢复时停止写服务，恢复匹配的数据库和文件集合，通过验证后切换连接配置与文件目录，再开放服务。失败保留原数据库和目录供回退，记录备份之后可能丢失的写入范围。

此方案是定期逻辑备份；若以后要求按时间点恢复，需要另行设计 PostgreSQL 基础备份、WAL 归档和媒体保留策略，不把逻辑备份描述为已有 PITR 能力。

发布前校验 storageVersion。迁移先备份再事务执行，未知版本拒绝启动写服务。代码回滚必须确认旧代码能读取当前数据库；不支持时先停止服务，再显式恢复数据库和匹配文件集合，不能只切软链接继续写。

## 14. Fork 维护策略

后端仓库不参与前端 upstream 合并，但前端写入协调、启动恢复、域 codec、脚本参数仍是长期维护点。

维护一份前端改动清单，按独立提交拆成：
- Cloud API、媒体工具和设置。
- 域快照编码与备份。
- 写入协调/flush/启动闸门。
- 恢复 journal 和回滚。
- 脚本说明及验收。

在隔离分支合并上游并对照本地数据写入清单。特别检查新增 localforage.setItem/removeItem/clear、延迟保存、自动清理和新插件数据；发现绕过协调器的写入就不能发布覆盖恢复。

不承诺独立后端意味着零冲突。每次同步上游检查数据类型、业务域、模型脚本变量与启动流程。进入 main 仍遵守项目明确合并确认规则，不推荐对已共享 main 随意 rebase/force push。

## 15. 合同产物与开发顺序

独立后端仓库的第一项提交必须包含：
- OpenAPI 全端点、请求/响应、鉴权、错误与分页 Schema。
- Manifest v1、四域 v1、mediaRefs Schema。
- 有效/无效清单夹具、含引用的真实脱敏样本。
- 状态机与错误码枚举。
- 锁定依赖与运行版本。
- 数据库迁移和升级拒绝测试。

顺序：
1. 状态、鉴权、配置校验、PostgreSQL 初始化。
2. 媒体 resolve/upload/private read 与并发一致性。
3. access grants、GET/HEAD/Range 与撤销。
4. 前端 Cloud 工具，真实渠道参考文件测试。
5. 四域 codec、文件完整性检查、不可变快照接口。
6. 写入协调器及全写入入口审计。
7. 捕获、上传和备份 UI。
8. 恢复 journal、启动恢复与回滚；通过故障测试后才开放覆盖恢复按钮。
9. 公网、回滚演练及独立部署文档。

阶段一不要求同时完成主体库、UI 全面重设计或自动同步。后端 media 能力通过即可先交付；backups/restore capability 必须与真实验收状态一致。

## 17. 可观测性与用户状态

UI 显示连接身份、已选域、捕获/哈希/上传/提交阶段、已完成字节数、取消状态、快照 ID。列表失败不能显示“没有备份”。

恢复时显示替换范围和原数据副本；成功只在回读验证与新启动通过后显示。仍在回滚显示“正在恢复原数据”，不能提前声称安全完成。

监控记录 ready 文件数、已提交快照数、存储余量、请求错误数、恢复失败数；禁止用指标推断自动删除策略。服务重启后可查看未完成上传、draft 和维护任务，由管理员处理。

## 18. 保留的扩展边界

- 主体库以后新增 subjects 域与 codec，不改现有域含义。
- 多用户模式增加账号会话；资源查询已按 workspace 隔离，但注册、权限模型另行设计。
- 对象存储替代磁盘时保持 mediaId、私有读取和 access-grant 契约，调整存储发布一致性实现。
- 自动双向同步需要删除与冲突协议，不把快照恢复偷偷改成 merge。
- 配置/脚本备份需要专门的敏感字段与可执行内容确认，不把整个 config store 塞入 Manifest。
- 未来新格式须先验证老快照与现有用户数据保护策略；不对本地存储做无需求迁移。

## 19. 待确认的生产策略：无静默默认值

| 配置 | 适用环节 | 未确认时 | 超限/失败行为 |
| --- | --- | --- | --- |
| MAX_IMAGE_BYTES / MAX_AUDIO_BYTES / MAX_VIDEO_BYTES | 上传与客户端预检 | 相关上传能力关闭 | 413，保留本地文件 |
| MAX_MANIFEST_BYTES / MAX_RECORDS / MAX_JSON_DEPTH | 创建快照 | 快照创建关闭 | 拒绝清单，不截断数据 |
| WORKSPACE_QUOTA_BYTES / MIN_FREE_DISK_BYTES | 上传、PostgreSQL、临时存储 | 写能力关闭 | 507，保留已有数据 |
| DB_POOL_MAX / DB_CONNECT_TIMEOUT_MS | PostgreSQL 连接池与获取连接 | 需明确配置 | 有界等待后 503，不泄漏连接 |
| DB_STATEMENT_TIMEOUT_MS / DB_LOCK_TIMEOUT_MS | PostgreSQL SQL 执行与锁等待 | 需明确配置 | 回滚事务，返回可识别错误 |
| DB_TX_RETRY_ATTEMPTS / DB_TX_RETRY_BACKOFF | 可重试数据库事务 | 不自动重试 | 保留幂等标识，查询或手动重试 |
| MAX_UPLOAD_CONCURRENCY | 同一客户端上传 | 需明确配置 | 客户端排队 |
| MAX_SERVER_UPLOADS | 服务端同时接收 | 需明确配置 | 429，不无界占内存 |
| REQUEST_TIMEOUT_MS / UPLOAD_TIMEOUT_MS | 前后端及代理 | 需明确配置 | 中止、可查询/重试，不报成功 |
| RETRY_ATTEMPTS / RETRY_BACKOFF | 幂等上传与查询 | 不自动重试 | 展示手动重试 |
| ACCESS_URL_TTL_SECONDS | 模型下载授权 | 禁止签发 | 过期拒绝；重新申请不修改原任务 |
| MAX_RESOLVE_BATCH / PAGE_SIZE | 摘要检查与列表 | 接口能力关闭 | 分批/分页，不截断清单 |

上述为生产行为策略，不是要求在文档阶段逐项打断用户。实施可先完成接口和测试配置；未确认生产值不得直接启用服务对外写入。Nginx、multipart 库和应用限制必须一致检查，避免隐藏默认上限截断文件。

## 20. 完成定义

只有以下条件满足，才能把设计对应阶段标记为已完成：
- 契约 Schema、数据库约束、端点和错误码一致。
- 清单所有媒体引用能够被校验、上传、下载和重建。
- 当前代码所有恢复相关写入入口已纳入协调，并通过崩溃/跨标签页测试。
- API Key 与云端令牌没有被应用自动序列化进快照。
- 公网链接、真实渠道输入格式分别验证，不凭模型名称推断协议。
- 生产行为策略经确认并显式配置。
- 部署、数据备份、代码回滚和数据库恢复均有验证记录。
- 未启用 Cloud 的现有本地模式、WebDAV 和旧模型脚本回归通过。
- 实施过程中发现契约缺口先更新本文件/后端契约，不用临时兜底掩盖失败。

文档解决的是开发歧义与已识别风险；测试和实际验收负责验证实现。任何未通过的关键项都必须保留为未完成，不能以“接口返回 200”替代整体可用性。
